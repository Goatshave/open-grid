# Open Grid 1.0 실행 로드맵

작성일: 2026-10-25 (Asia/Seoul). 기준 소스: #41 병합 커밋
`f8d13722b0d5622e60c8a3e0a663aefe9b47df7b`.

이 문서는 1.0 개발을 시작하기 위한 실행 계획이다. 체크되지 않은 항목은
미완료이며, 일정이나 현재 지원 기능을 약속하는 출시 안내가 아니다.
진행 상황과 범위 변경은 이 문서의 작업 ID에 기록한다.

## 1. 목표와 판정 방법

**1.0은 일반적인 상용 업무 제품이 그리드를 채택하고 장기간 유지할 수 있는
버전으로 만든다.** 기본 표 기능에 더해 운영 화면, 대량 편집, 서버 데이터,
분석·내보내기까지 완결된 사용 흐름을 제공한다.

동급 여부는 기능 이름의 개수보다 다음 결과로 판정한다.

- 기본 업무 기능과 아래 P0/P1 범위를 실제 제품 흐름에서 사용할 수 있다.
- React, Vue, Svelte에서 같은 기능·이벤트·오류 복구·접근성 계약을 제공한다.
- 빠른 입력, 재시도, 충돌, 쿼리 변경, 화면 이동에도 데이터와 사용자 초안이 보존된다.
- 대용량·장시간 사용에서 성능과 자원 사용량을 재현 가능한 증거로 설명한다.
- 공개 API, 마이그레이션, 설치·배포, 문서와 유지보수 정책을 신뢰할 수 있다.

우위를 목표로 할 영역은 **세 프레임워크의 기능 일치, 기본 UI와 headless의
동시 제공, 비동기 데이터 무결성, MIT 배포, 선택적 기능의 가벼운 도입**이다.
이는 개발 목표다. 경쟁 제품보다 빠르거나 우수하다는 공개 주장은 별도 비교
검증을 통과한 범위에서만 한다.

## 2. 기준 제품과 현재 출발점

공식 문서를 2026-10-25에 확인했다. 아래는 범위를 정하기 위한 문서 기반
비교이며 실측 성능 비교나 모든 에디션의 기능 동등성 판정은 아니다.

| 기준 | 확인한 관점 | Open Grid에 적용할 목표 |
| --- | --- | --- |
| [AG Grid Community / Enterprise](https://www.ag-grid.com/react-data-grid/community-vs-enterprise/) | 기본 업무 그리드와 그룹·분석·서버·상세 화면 등 고급 사용 흐름의 폭 | 기본 기능뿐 아니라 피벗, 상세 행, 서버 연동, 업무용 내보내기까지 범위에 포함 |
| [TanStack Table 개요](https://tanstack.com/table/latest/docs/overview), [기능 구성](https://tanstack.com/table/latest/docs/guide/features) | headless 엔진과 선택 가능한 기능 구성 | 공개 코어 계약, 확장성, faceting·행 고정·셀 병합 등 기능 구성 검토 |
| [MUI X Data Grid](https://mui.com/x/react-data-grid/) | 완성된 기본 UI, 커스터마이징, 업무·분석 흐름 | 필터·편집·패널을 제품이 매번 재구현하지 않아도 되는 기본 경험 |
| [WAI-ARIA APG Grid](https://www.w3.org/WAI/ARIA/apg/patterns/grid/) | 키보드 탐색, 셀 내부 조작과 편집, 가상화된 구조의 의미 전달 | 포커스·편집·선택·가상화가 함께 동작하는 접근성 검증 |

현재 소스에는 정렬, 그룹/집계, 트리, 열 관리, 행/열 가상화, 단일 범위 선택,
셀 편집·히스토리, CSV/TSV, 테마·로컬라이제이션, 서버 요청 수명주기가 있다.
#41은 IME, 커스텀 에디터, 숫자/날짜/집합 필터, 저장 순서·복구, 알 수 없는
총건수, 쿼리 단위 선택·일괄 처리와 실제 HTTP 예제를 더했다.

| 영역 | 기준 소스의 상태 | 1.0에서 채울 간극 |
| --- | --- | --- |
| 편집 | 셀 편집, 동기 검증, 커스텀 에디터, 로컬 undo/redo, 비동기 저장 예제 | 행/일괄 편집, 비동기 검증, 저장 중 초안·트랜잭션·오류 UX의 공통 계약 |
| 필터 | 텍스트, 숫자/날짜 범위, 집합, 사용자 함수 | 연산자·AND/OR 조건 모델, 조건 UI, 필터 후보와 개수, 서버 직렬화 |
| 서버 데이터 | 수동 쿼리, 페이지 요청, 취소/재시도, 예제별 그룹/트리/저장 | 재사용 가능한 datasource, 블록 캐시·무한 로딩, 갱신·무효화·증분 변경 |
| 행/셀 배치 | 열 고정, 가변 높이, 그룹 헤더의 span | 행 고정·행 이동·상세 행·본문 셀 span과 가상화의 공존 |
| 분석 | 그룹/집계/그룹 푸터 | 피벗 행/열 축, 동적 결과 열, 합계·소계, 설정 UI |
| 선택/클립보드 | 행 선택, 단일 셀 범위, TSV 복사/붙여넣기, 채우기 | 다중 범위·잘라내기, 복합 입력, 실패·읽기 전용 셀의 예측 가능한 처리 |
| 파일/인쇄 | CSV/TSV와 서버 스트리밍 | XLSX, 데이터형·서식·헤더 보존, 인쇄용 표현과 대량 작업 제한 |
| 국제화/접근성 | 라벨 번역, 키보드, 자동 접근성 검사 | RTL, locale별 입력/표시, 실제 IME·클립보드·보조공학 검증의 확대 |
| 제품 채택 | 예제, API 스냅샷, 패키지 소비·릴리스 게이트 | 실제 제품 통합, 안정 API, 유지보수 약속과 재현 가능한 업그레이드 |

근거는 `packages/core/src/types.ts`, `grid.ts`, `column-filter.ts`,
`server-mutation.ts`, `server-selection.ts`, 각 UI 패키지와 현재 가이드다.
간극은 공개 계약·예제·완료 증빙이 아직 확인되지 않은 영역을 뜻한다.
키워드 검색만으로 모든 내부 구현의 부재를 단정하지 않으며 M0에서 상세 확인한다.
특히 그룹 헤더 span을 본문 셀 병합으로, 수동 서버 모드를 캐시형 서버 row model로
간주하지 않는다.

## 3. 우선순위와 개발 규칙

| 우선순위 | 의미 |
| --- | --- |
| P0 | 데이터 무결성, 코어 계약, 기본 업무 UX, 접근성·배포 안전성. 선행 필수 |
| P1 | 1.0의 폭과 경쟁력을 만드는 고급 업무 기능. **현재 1.0 목표의 필수 범위** |
| P2 | 후속 확장 후보. 구체적 수요와 별도 범위 결정 후 진행 |

P1은 시간이 부족하면 자동으로 생략하는 목록이 아니다. 축소가 필요하면 목적,
사용자 영향, 대안과 다음 목표를 기록하고 범위를 다시 합의한다.

작업 순서는 M0 → M1 → M2 → M3 → M4 → M5 → M6 → M7 → M8이다.
접근성·세 프레임워크 검증은 각 단계에 포함하며 마지막 단계로 미루지 않는다.
단계 안에서는 실패 회귀 → 계약/설계 → 코어 → 렌더러 → 예제/문서 → 검증 순서로
완결된 수직 작업을 만든다. 새 공개 모델은 구현 전에 타입 예시와 상태 전이를 검토한다.

마일스톤과 npm 버전은 다르다. 기능마다 작은 minor를 발행하지 않고, 사용자에게
완결된 가치를 전달하는 묶음으로 0.x를 릴리스한다. 날짜·인력·기간은 M0 분해 후
실측해 정하며, 근거 없는 출시일을 두지 않는다.

## 5. 측정 가능한 품질 기준

| 항목 | 판정 기준 |
| --- | --- |
| 기존 성능 | [현재 성능 정책](performance.md)의 번들·DOM·heap·100k/1m 코어·서버 게이트 유지. 예산 상향은 실측 귀속과 별도 검토 필요 |
| 새 UX 목표 | 고정된 장비·브라우저·데이터에서 기본 10k × 20 셀 상호작용 p95 ≤ 100ms, 가상 스크롤 frame p95 ≤ 32ms를 후보 목표로 검증. M0에서 측정법·분산·유효 범위를 정한 뒤 반복 재현 가능한 항목만 강제 게이트화 |
| 서버 규모 | 1천만 논리 행 fixture에서 제한된 블록만 로드하고 캐시/요청/DOM 상한 준수. 1백만 브라우저 행 전체 마운트나 전체 다운로드를 의미하지 않음 |
| 장시간 변경 | 초당 100개 sparse row update를 60초 적용하는 목표 워크로드를 정의하고 데이터 일치·입력 응답·메모리를 함께 측정. 실제 지원 한도는 측정 결과로 문서화 |
| 수명주기 | mount/unmount 100회, 쿼리 교체·취소 1,000회 후 구독/관찰자/요청 정리. warmup 이후 강제 GC 조건에서 retained heap 증가 5% 이내를 후보 기준으로 검증 |
| 무결성 | 편집/검증/조회/저장/일괄 작업의 지연·역순·응답 유실·중복·취소·충돌을 결정적으로 재현. 중요 경로는 상태 전이와 실제 결과가 일치해야 함 |
| 접근성/입력 | Chromium/Firefox/WebKit 자동 검사 + 실제 macOS VoiceOver/Safari, Windows NVDA/지원 브라우저, 한국어/일본어 IME·OS 클립보드 검토. 접근성 적합성을 자동 검사만으로 선언하지 않음 |
| 외부 소비 | 깨끗한 별도 프로젝트의 설치·타입·ESM·UI 실행·SSR/hydration·업그레이드, 10개 기존 패키지와 승인된 추가 패키지의 정합성 |
| 유지보수 | 필수 CI 성공, 미검토/만료 보안 예외 0건, 변경 기록·마이그레이션·지원 매트릭스와 최종 source revision 연결 |

현재 통과한 기존 게이트와 앞으로 검증할 후보 목표를 구분한다. 브라우저 시간 측정은
기존 정책처럼 안정성을 확인한 뒤 강제 기준으로 승격한다. 경쟁 제품 성능 비교는
별도 독립 benchmark 프로젝트에서 같은 기능·데이터·장비·설정으로 수행하며,
이 저장소에 비교 제품 의존성을 추가하지 않는다.

## 6. 후속 후보와 범위 변경

P2 후보는 범용 수식 엔진, 통합 차트·sparkline, AI 기능, 실시간 공동 편집/CRDT,
완전한 Excel 호환, 새로운 프레임워크 어댑터다. 각각 독립적인 제품·비용·계약을
요구하므로 1.0의 공통 업무 그리드 목표와 분리해 수요와 증거로 우선순위를 정한다.

범위가 바뀌면 작업 ID, 사유, 영향받는 API/사용 흐름, 다음 목표, 새 승인 기준을
기록한다. 편의상 체크하거나 1.0 날짜에 맞추려고 품질 기준을 낮추지 않는다.

## 7. 다음 작업과 완료 증거

**`BASE-02`는 완료했다.** [현황표](reviews/1.0-capability-matrix.md)에 현재 기능
32개와 필수 간극 20개를 소스·가이드·예제·자동/수동 검증·후속 작업 ID에 연결했다.
[API-01 범위](reviews/1.0-api-01-scope.md)는 안전한 ID 인덱스(A), 정의 검증(B),
데이터/스키마 교체와 수명주기(C)로 분해했다. A의 구현·로컬 검증은 완료했으며
B/C는 설계 초안이다. API-01 전체는 완료되지 않았다.

사용자가 지시한 `API-01-A`의 ID 인덱스 안전성 보완과 회귀 추가를 완료했다.
작업 범위 문서에 baseline 실패/수정 후 통과, 타입·어댑터·브라우저·패키지 소비와
성능 검증을 기록했다. 원격 CI 결과는 PR에서 별도로 확인한다.
M0의 `BASE-03` 최종 수동 검토/출시 준비와 `BASE-04` 새 측정 기준 확정은
완료로 처리하지 않고 별도로 유지한다.
작업 브랜치는 기여 가이드의 `docs/`, `fix/`, `feat/` 등 표준 유형 접두사를 따른다.

각 작업은 다음 기록을 함께 갱신해야 완료로 표시한다.

| 기록 | 내용 |
| --- | --- |
| 작업 | ID, 상태(todo/in-progress/blocked/done), 선행 작업, 범위와 비범위 |
| 계약 | 공개 타입/옵션/이벤트, 기존 동작과 마이그레이션, 상태 전이 |
| 구현 | 변경한 패키지·예제·문서, PR과 소스 커밋 |
| 검증 | 실행 명령, 환경, 실제 결과, 실패/복구·브라우저·수동 증거 |
| 제한 | 알려진 제한과 이슈, 사용자 영향, 출시 차단 여부 |

현재 완료 증거(`BASE-01`): [#41 병합](https://github.com/Goatshave/open-grid/pull/41),
위 기준 소스/공식 문서 조사,
