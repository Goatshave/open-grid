# 0.4 workflow review and delivery scope

Reviewed on 2026-10-24 (Asia/Seoul), against merged `main` revision
`a686580311c1918c684154ab54eaa41e75f1630b`, with public package version 0.3.0.
The scope was accepted for development on 2026-10-24. The findings below describe
the reviewed 0.3 baseline; implementation progress is recorded separately below.

## Release goal

Make server-backed lists and editing usable through loading, repeated actions,
failure, and recovery across React, Vue, and Svelte. The release should deliver
complete user workflows, with several implementation PRs contributing to each
outcome. Individual PRs do not require individual minor releases.

The review used source inspection, the existing browser coverage, three live local
reference UIs, and direct calls to the rebuilt core package. It did not include
production backend integration, external user research, or a new manual
screen-reader review. Priorities reflect observable integration gaps, rather than
measured customer demand or a comparison with other grid products.

Local checks used Node 22.19.0, pnpm 9.15.0, and desktop Chrome 155 on macOS.
Core probes were repeated after rebuilding `@open-grid/core` from the reviewed
revision. Browser probes used the maintained Vite development examples and held
only the mock save callbacks; no repository runtime source was changed.

## Findings

### F1: older cell saves can replace newer values in all three reference examples

The general cell-edit examples keep the editor open during a simulated server save.
Another Enter commit can start a second save. Each completion unconditionally
updates row data and clears editing/focus state. There is no per-cell ordering or
revision check in these handlers.

Browser reproduction:

1. Open the reference example and its server-owned text cell: React
   `INV-0001/customer`, Vue or Svelte `REG-001/city`.
2. Hold the mock save completions by intercepting only their 160 ms timers.
3. Submit `Scope First Save`, then submit `Scope Second Save` in the open editor.
4. Resolve the second save first, then the older first save.

| Renderer | After second save completes | After older first save completes |
| --- | --- | --- |
| React | `Scope Second Save` | `Scope First Save` |
| Vue | `Scope Second Save` | `Scope First Save` |
| Svelte | `Scope Second Save` | `Scope First Save` |

The final visible value and saved-status message both revert to the older value.
This is a reproduced defect in the product-owned reference save flow, not evidence
that the core performs server writes. The probes reorder simulated completions;
they do not demonstrate a production database race.

Source: [React save handler](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/examples/react-basic/src/main.tsx#L638),
[Vue save handler](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/examples/vue-grouped/src/main.ts#L432),
[Svelte save handler](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/examples/svelte-grouped/src/App.svelte#L374).

### F2: ordinary server editing covers successful saves only

The same mock save functions always resolve. Their callers have success handlers
but no rejected-save recovery path. Existing editor tests cover invalid input,
pending/successful direct saves, and asynchronous paste success. A paste intercepted
for server approval is reported by the synchronous core summary as skipped, even
after the product later saves it; there is no separate asynchronous operation
summary in these examples.

This is an integration and coverage gap. The review did not inject a rejected
transport into these timer-only mocks. The proposed work needs a testable transport
that can return validation errors, transient failures, and revision conflicts.
Existing tree rollback/conflict handling is a useful reference, but does not supply
the ordinary editable-cell flow.

Source: [React mock transport](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/examples/react-basic/src/main.tsx#L343),
[existing edit/paste coverage](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/e2e/react-grid.spec.ts#L450).

### F3: unknown-total server pagination has no first-class navigation contract

The public options support `manualPagination`, `pageCount`, and `rowCount`. They do
not accept an independent indication that another page exists. Without a supplied
count, core derives the page count from the currently loaded rows.

A direct probe using 25 loaded rows, page size 25, manual pagination, and neither
count returned:

```json
{ "rowCount": 25, "pageCount": 1, "canNext": false, "afterNextPage": 0 }
```

The current API does not claim cursor or unknown-total navigation support; this is
a feature gap, not a regression in exact-count pagination. Accessible unknown totals
already use `aria-rowcount="-1"`; that behavior must be retained.

Source: [public options](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/packages/core/src/types.ts#L515),
[page count and transitions](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/packages/core/src/grid.ts#L1235).

### F4: flat server examples do not exercise asynchronous list loading

The React, Vue, and Svelte flat ticket examples synchronously query in-memory data;
their asynchronous export work is separate. They demonstrate controlled sorting,
filters, totals, and pagination, but not list-fetch cancellation, stale responses,
retained rows after a failed refresh, or retry. The coordinator and tree examples
already supply much of the required infrastructure.

Source: [React flat list query](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/examples/react-server-side/src/main.tsx#L86),
[current request contract](../server-data#request-lifecycle).

### F5: server-wide selection needs an explicit query scope

Core preserves selection across data changes by design. In a direct probe,
`toggleAllRowsSelected(true)` followed by replacement data from a different query
also selected the new row. Selected row models materialize loaded rows, not every
matching record on a remote server.

This is expected under the existing contract. Product code must distinguish a page
change from a change in the selected universe. A future server-wide bulk-action
contract should carry query identity and excluded IDs, rather than enumerate all
remote rows or interpret a loaded selected-row model as the remote selection.

Source: [selection ownership and compact selection](../architecture#core),
[selection operations](https://github.com/Goatshave/open-grid/blob/a686580311c1918c684154ab54eaa41e75f1630b/packages/core/src/grid.ts#L1337).

## Accepted 0.4 delivery scope

### A. Reliable server-backed editing and bulk save

Deliver a shared, opt-in mutation lifecycle and maintained examples that cover:

- Per-cell ordering and revision-safe application of results; different cells can
  save independently. Correct the F1 example defect first and add browser coverage
  across all three renderers.
- Observable pending, saved, validation-error, transport-error, and conflict states,
  with accessible messages and retry/revert actions that preserve unsaved input.
- A transport boundary that can reject requests and return authoritative values,
  revision conflicts, and operation IDs. Demonstrate it with an actual local HTTP
  route; database/auth implementation remains product-owned.
- Multi-cell paste/save results with pending, successful, and failed cells tracked
  separately. A retry targets failed work and must not repeat successful mutations.
- Cleanup and navigation rules that prevent late responses from stealing focus or
  closing a newer editor. Preserve the current synchronous edit/paste contracts and
  local undo/redo behavior; document server-owned undo separately.

Design the mutation semantics explicitly. A read coordinator's replace-and-abort
behavior cannot guarantee cancellation or rollback of a server write. Serializing
writes, expected revisions, and idempotency require cooperation from the product
transport/server. Public helper names and exact types remain design work.

Acceptance: reproducible reversed completions, repeated Enter, rejection, conflict,
cross-cell concurrency, partial paste failure, retry, and unmount/navigation cases
pass in React, Vue, and Svelte. Existing local editing and history tests still pass.

### B. Complete asynchronous server-list integration

Deliver:

- Unknown-total navigation with an explicit next/previous availability contract.
  Preserve exact-count behavior and define what last-page controls and page labels
  mean when no total exists. Opaque cursors remain in product transport/query state.
- Flat remote-list examples in all three frameworks using the existing request
  coordinator for cancellation, stale-response protection, retained rows, and retry.
- Consistent committed-query versus pending-query presentation: old rows retained
  during loading/failure must not be labelled as a successfully loaded new page.
- Filter/sort reset rules, reduced totals, empty results, and independent selection
  handling for page changes versus query changes. Do not introduce an implicit
  global selection reset that breaks existing consumers.
- An end-to-end recipe from query construction through HTTP response and grid state,
  including accessible loading/error/pagination feedback.

Acceptance: known and unknown totals, final-page detection, rapid query changes,
out-of-order responses, failed refresh with retained rows, retry, empty data, and
filter/page transitions work consistently across the three renderers. Unknown
totals remain unknown to assistive technology.

## Expanded scope accepted on 2026-10-24

After A+B, deliver these in order as part of the same 0.4.0 release:

1. IME-safe keyboard handling, including React native events and composition-end 229.
2. A typed `renderEditor` contract in React/Vue/Svelte. Editors own draft/focus/blur;
   commit uses existing parsing, validation, preventable events and server approval.
   Cancellation and stale editor callbacks cannot change another active editor.
   Demonstrate a calendar editor and an account autocomplete with accessible errors.
3. Serializable numeric/date ranges and set filters, opt-in built-in controls,
   localization, client/server matching parity, and query/page reset behavior.
4. A separate opt-in server selection contract: explicit IDs or all matching rows
   under a query identity with exclusions. Keep page/sort changes separate from
   query changes and demonstrate a real server bulk action without downloading all IDs.
5. Chromium/Firefox/WebKit regression coverage for the expanded workflows and the
   existing release gates. Synthetic composition events do not replace actual IME
   review, and WebKit coverage does not claim a manual Safari check.

Public contracts and examples must be documented before the release. Existing
0.3 behavior stays compatible; consumers opt into new editor, filter, and selection APIs.

## Implementation order and release criteria

1. Correct F1 with focused regression coverage in the three reference examples.
2. Agree mutation ordering, failure, and result contracts; deliver A incrementally.
3. Define unknown-total navigation; deliver B using the existing read coordinator.
4. Validate both complete workflows together, update public API snapshots and guides,
   and run the existing artifact, consumer, performance, browser, and accessibility
   gates. Verify upgrade behavior from 0.3.

Use 0.4 as the release boundary for the completed A+B workflows and the expanded scope above. Compatible
correctness/security fixes can still ship in a patch when needed; they do not need
to wait for feature completion. Package versions remain 0.3.0 until separate release preparation.

For 1.0, require usable product integrations, explicit supported API/compatibility
contracts, documented recovery paths, and the existing release evidence. Once the
1.0 feature scope is complete, use `1.0.0-beta.N` for integration feedback, then
`1.0.0-rc.N` for release-blocking fixes, and finally `1.0.0`. An alpha is optional.
Prereleases use `next`; stable releases use `latest`, per
[API stability](../api-stability#version-policy).

## Implementation progress

- The reference cell-save race is corrected through shared per-key mutation ordering
  and current-intent checks. Browser coverage verifies repeated saves, newer drafts,
  and different active editors across React, Vue, and Svelte.
- Core now exposes the opt-in mutation coordinator and unknown-total manual
  pagination. Existing exact-count pagination and synchronous edit/paste contracts
  are retained.
- All three flat server examples now use local HTTP routes, revision-checked saves,
  failure/conflict recovery, and separate asynchronous partial-save summaries.
- Read responses retain their committed query/page, and acknowledged revisions fence
  older reads. Existing buffered/streaming export examples use the live server data.
- IME guards, custom editor contexts, typed filter controls, and query-scoped bulk
  selection now work in React, Vue, and Svelte. Cross-engine regressions caught and
  corrected a Vue/WebKit pressed-text replacement and stale selection projection.
  The Vue fix keeps the first content node stable without adding empty per-cell nodes.
- React's built-in editor seeds a draft once per edit session. A previous save's
  acknowledgement cannot reset newly typed text when its row update propagates.
  The regression waits for save status and settled frames, and verifies that a
  cancelled/reopened editor still starts from the acknowledged value.
- Public API snapshots, migration notes, and automated verification accompany the
  implementation. Publication and source-bound manual release approval remain
  separate release steps; no 0.4 package has been published by this work.
