# API-01 — ID·상태·수명주기 계약의 첫 작업 범위

상태: **A 구현·로컬 검증 완료, B/C 설계 초안**. 2026-10-25.
근거: [BASE-02 현황표](1.0-capability-matrix.md)의 C02/C03/C32와 5절 탐침.
상위 [로드맵](../roadmap-1.0.md)의 M0 선행 기준을 확인하고 M1 구현에 사용한다.

## 목적

그리드의 선택·편집·포커스·히스토리가 같은 행/열을 일관되게 참조하도록 한다.
새 기능을 추가하기 전에 ID 조회와 외부 데이터 교체의 의미를 명확히 만든다.
이를 A/B/C의 작은 수직 작업으로 나누고 각 작업에 회귀·문서·호환성을 함께 둔다.

## API-01-A — 안전한 행 ID 인덱스

첫 구현은 `rowsById`의 저장/조회 안전성이다. 사용자 지시로 M0의 남은
출시/측정 작업과 구분해 이 호환성 보완을 먼저 진행한다. `__proto__` 입력이
own entry가 되지 않던 baseline 관찰을 의미 있는 회귀로 만들었다.

범위:

- flat/nested/lazy 및 필터·정렬·그룹·펼침 이후 row model의 ID 인덱스를 조사한다.
- prototype 이름(`__proto__`, `constructor`, `toString`, `hasOwnProperty`)도
  실제 행 ID로 저장/조회되며 없는 이름은 상속 프로퍼티를 행으로 반환하지 않게 한다.
- 공개 `RowId = string`, `rowsById: Record<RowId, Row<TData>>` 형태를 유지한다.
  내부 Map을 그대로 새 공개 API로 노출하지 않는다.
- null-prototype record 등 dictionary 방식을 검토하고 직접 프로퍼티,
  `Object.keys/values/hasOwn`, JSON 직렬화와 소비자 호환성을 확인한다.
- 실제 선택·편집·export 등 ID 조회 사용 흐름과 lazy 인덱스의 성능을 검증한다.

완료 증거: baseline에서 실패하고 수정 후 통과하는 코어 회귀, 타입/API 계약,
세 어댑터 소비·기존 동작, 코어 규모/할당 비용 검증과 변경 기록.
새 열/행 유일성 강제 정책과 데이터 교체 자동 cleanup은 이 작업에 섞지 않는다.

권장 브랜치/PR 범위: `fix/row-identity-index` — 안전한 record 조회를 완결하는
호환 가능한 보완. 실제 구현 검토에서 호환 영향이 드러나면 먼저 migration 범위를 수정한다.

### 구현 내용

- eager/lazy `rowsById`를 null-prototype record로 구성하고 지연 생성·캐시를 유지한다.
- 선택·펼침 플래그는 own property만 읽는다. 상태 record는 일반 객체를 유지하고,
  `__proto__` 쓰기만 data property로 정의해 저장한다. 이 경로는 compact 전체 선택의
  제외/정리와 원격 선택 projection에도 적용한다.
- 공개 exports/타입을 추가하거나 ID를 재발급하지 않는다. 중복 ID 검증, 열 ID 정책,
  데이터 교체의 상태 자동 정리는 B/C로 남긴다.
- 인덱스·사용 흐름 회귀(`packages/core/test/row-identity.test.ts`) 13개는
  분리된 기준 소스(`f8d1372`)에서 모두 실패하는 것을 확인했다. 추가로 서버 선택과
  React/Vue/Svelte 어댑터에 특수 ID 소비 회귀를 연결했다.
- [dictionary 사용 가이드](../api-stability.md#row-ids-and-row-model-dictionaries)에
  `Object.hasOwn`, own flags, JSON projection과 기존 객체 메서드 사용의 전환을 기록했다.

### 로컬 검증 기록

2026-10-25, Node 22.19.0 / macOS에서 기준 소스 `f8d1372`와 작업 트리를
검증했다. 이 기록은 원격 CI나 게시 완료 증거가 아니다.

- `pnpm test`: 전체 통과. 코어 134개이며 새 코어 회귀 14개와 세 어댑터 회귀
  각 1개(총 17개)를 추가했다. ID 인덱스/사용 흐름 13개는 분리된 기준 소스에서
  모두 실패하고 수정 후 통과했다.
- `pnpm build`, `pnpm check`, `pnpm api:check`, `pnpm compatibility:check`:
  통과. 공개 declaration/exports 스냅샷은 변경하지 않았다.
- 전체 E2E 185개, UI/접근성 smoke 36개, Chromium/Firefox/WebKit 통합 45개 통과.
  `pnpm docs:build`도 dead-link 검사를 포함해 통과했다.
- 기존 bundle/DOM/heap 예산 통과. 코어 대용량 게이트는 첫 실행의 전역 필터
  p95 배율이 2.149x로 2.000x 기준을 넘었다. 단독 재측정에서 1.958x로
  모든 항목이 통과했다. 예산은 변경하지 않았으며 p95의 측정 변동은 남아 있다.
- 서버 standard/stress 예산과 framework/server benchmark 동작 회귀 각 1개 통과.
- `pnpm release:check`의 10개 패키지/16개 예제와 pack dry-run, 임시 `0.4.0`
  tarball 10개의 외부 소비 검사(설치·ESM import·타입·Svelte build) 통과.
  실제 저장소 버전은 `0.3.0`을 유지했으며 npm 게시를 수행하지 않았다.

지연 인덱스가 실제 생성되는 비용도 별도로 비교했다. `rows.ts`만 같은 TypeScript
설정으로 변환한 기준/수정 모듈을 별도 Node 프로세스에서 실행했다. `row:<n>`
문자열 ID의 flat row를 미리 만들고, 매회 새 lazy 모델의 `rowsById`를 처음 읽었다.
2회 준비 후 7회 측정, `--expose-gc`로 생성 전후 GC를 수행했으며 own key 수와
캐시 재사용을 검증했다. 아래 메모리는 기존 row를 제외한 인덱스의 유지 heap 차이다.

| 행 수 | 기준 생성 중앙값 | 수정 생성 중앙값 | 기준 / 수정 유지 heap |
| --- | ---: | ---: | ---: |
| 100,000 | 5.762 ms | 5.361 ms | 6,291,600 / 6,291,600 bytes |
| 1,000,000 | 99.053 ms | 93.189 ms | 50,331,792 / 50,331,792 bytes |

이 단독 관찰은 인덱스 할당의 회귀 여부를 확인하기 위한 것이며 성능 향상 보장이나
새 강제 예산으로 사용하지 않는다. 생성되지 않은 lazy 인덱스의 비용과 혼동하지 않는다.

## API-01-B — ID 유일성·정의 검증

현재 두 행/열의 ID가 겹치면 일부 인덱스가 마지막 값을 사용한다. 유효한 ID와
중복 정의 처리 정책을 공개 계약으로 정한다.

- 위치 fallback은 유지하고, reorder/insert/delete/서버 데이터에는 안정적인
  `getRowId` 사용을 가이드와 예제로 보여준다. 자동 UUID로 조용히 교체하지 않는다.
- 사용자 행 ID의 전체 트리 범위 유일성, 빈 문자열/잘못된 runtime 타입,
  synthetic 그룹/푸터 ID와의 충돌을 검토한다.
- 열 그룹/leaf, accessor/display 열의 ID 결정 순서와 유일성 범위를 정한다.
- 오류는 어느 정의/경로가 충돌하는지 알 수 있어야 하며 별도의 개인정보를 출력하지 않는다.
- 기본값을 바꾸어 기존 허용 입력을 거부한다면 호환 변경으로 포장하지 않는다.
  pre-1.0 minor 경계·migration 예시·API/changelog를 함께 검토한다.

완료 증거: 잘못된 입력과 정상 nested/grouped 입력의 회귀, 자료 교체/정렬 시 안정
ID 시나리오, 프레임워크 예제, 명시한 오류/진단 방식과 성능 비용.
구체적인 옵션명과 오류 타입은 이 초안에서 새 공개 API로 확정하지 않는다.

## API-01-C — 외부 데이터/스키마 교체와 수명주기

`setOptions`, `setState`, 제어 상태의 proposal과 반영 순서, callback/구독의
책임을 정리하고 동작 차이를 테스트한다.

- 기존 행의 값 변경, client 행 삭제, server page-off, query 변경, 열 삭제를
  구분한다. 화면 밖 행 선택을 지워 원격 선택을 잃는 자동 cleanup은 피한다.
- 사라진 셀의 focus/edit/range, 히스토리와 저장 중 draft가 어떻게 끝나거나
  유지되는지 결정한다. 제어 상태는 제품이 거절/갱신할 수 있는 경로를 명시한다.
- Vue scope/수동 dispose, Svelte readable/options unsubscribe, React effect cleanup,
  coordinator dispose를 구분한다. 현재 core `Grid.dispose`가 있는 것으로 설명하지 않는다.
- 이벤트/구독 재진입과 예외, unmount 후 비동기 완료의 허용 동작을 검토한다.
  측정 없이 공통 lifecycle API를 추가하거나 모든 제품 상태를 코어로 옮기지 않는다.

완료 증거: client delete vs server page 전환, schema 교체, 제어/비제어 feedback,
adapter cleanup과 StrictMode, 새 draft/원격 ack의 교차 흐름을 재현한 회귀와 가이드.
